# 로컬 실행 명령어

모든 명령은 저장소 루트(`MCP_Capstone/`)에서 실행한다.

## 스크립트 한눈에

| 하고 싶은 일 | 명령 | 하는 일 |
| --- | --- | --- |
| 내 PC에서 개발 | `scripts/run_all.sh` | 백엔드·MCP 2개·에이전트·관리자 화면. `MCP=0`이면 MCP 없이 |
| 팀·기획팀에게 공개 시연 | `scripts/run_public.sh` | `.env`를 운영 모드로 맞춤(처음 한 번 Slack 값 입력) → DB 준비 → `run_all.sh` + Slack 봇 + 터널 |
| 이미 띄운 서버에 터널만 | `scripts/tunnel.sh` | Quick Tunnel 열기, 끊기면 다시 열기. Cloudflare 계정에 로그인된 PC면 고정 주소도 이 PC로 연결 |
| DB를 시드 상태로 | `db/reset.sh` | `app` 스키마를 지우고 다시 만든 뒤 시드 적재 (데이터 삭제) |

## 처음부터 전부 켜기

1. Docker Desktop 켜기
2. `docker compose up -d postgres`
3. `scripts/run_all.sh`
4. (새 터미널) `uv run python -m apps.slack_bot`
5. (외부 공개가 필요할 때) 1~4 대신 `scripts/run_public.sh` 하나로 띄운다

## 외부 공개 (고정 주소)

- 화면은 Cloudflare Workers(`apps/admin_web/wrangler.jsonc`)가 낸다. GitHub main에 push하면 Workers Builds가 자동으로 빌드·배포한다.
- `/api/*`는 Worker(`apps/admin_web/worker.js`)가 로컬 서버로 넘긴다. 로컬은 Quick Tunnel이라 주소가 매번 바뀌므로 `scripts/tunnel.sh`가 새 주소를 KV에 적는다 (반영까지 최대 1분).
- 로컬 서버나 터널이 꺼져 있으면 고정 주소는 화면만 뜨고 API는 503을 낸다.
- 수동 배포: `cd apps/admin_web && npm run build && npx wrangler deploy`

## 1. DB (Postgres)

```bash
docker compose up -d postgres                    # DB 켜기 (Docker Desktop 필요)
docker compose ps                                # 127.0.0.1:5432->5432 매핑이 보여야 정상
docker compose up -d --force-recreate postgres   # 포트 매핑이 빠졌을 때 재생성 (데이터 유지)
db/reset.sh                                      # 스키마·시드 초기화 (데이터 삭제됨)
```

## 2. 서버 (백엔드 · MCP · 에이전트 · 관리자 화면)

```bash
scripts/run_all.sh                          # 한 번에 켜기. 같은 터미널에서 Ctrl+C로 전부 종료
MCP=0 scripts/run_all.sh                    # MCP 서버 없이 (에이전트가 백엔드 REST 직접 호출)
pkill -f 'uvicorn apps\.|apps\.mcp_|vite'   # 다른 터미널에서 끌 때
```

- `.env`를 바꾸면 끄고 다시 켜야 반영된다.
- 화면 http://localhost:5173 · 백엔드 http://localhost:8000/docs · 에이전트 http://localhost:8002/docs

### Slack + 외부 웹 시연을 한 번에 실행

```bash
scripts/run_public.sh
```

처음 실행하면 터미널에서 본인 Slack ID, 연결할 직원 ID, Slack Bot Token, App Token을 입력한다. 토큰은 화면에 표시되지 않고 `.env`에 저장된다. 이미 입력한 값은 다시 묻지 않는다. `SLACK_USER_MAP`이 비어 있으면 `SLACK_USER_ID` → `SLACK_EMPLOYEE_ID` 한 명으로 연결하고, 이미 있는 매핑은 그대로 쓴다.

외부에 공개되므로 `.env`를 운영 모드로 맞춘다: `APP_ENV=prod`, `JWT_SECRET`(없으면 생성), `SYSTEM_TOKEN`(서명된 JWT 발급). 그래서 로그인은 사번 + 비밀번호(시드 `DEMO_PASSWORD`)로 한다. `run_all.sh`는 `APP_ENV=prod`가 아니면 `TUNNEL=1`을 거부한다.

> ⚠️ 같은 Slack 앱 토큰으로 봇을 두 대 이상 띄우면 Slack이 메시지를 아무 봇에게나 나눠 준다. 시연 중에는 봇을 한 PC에서만 띄운다.

이 명령은 로컬 PostgreSQL, 백엔드, 에이전트, 관리자 화면, Slack Socket Mode 봇, Cloudflare 임시 터널을 함께 시작한다. DB 스키마가 없을 때만 시드 초기화를 실행하고, 기존 DB는 지우지 않는다. 출력된 주소는 `logs/cloudflare.log`에서 확인한다. Slack 요청과 웹 요청은 같은 로컬 DB의 `agent.tasks`에 저장되며, 동료마다 자신의 Slack ID와 직원 ID를 설정하면 요청자별 이력이 분리된다.

실행 순서:

```text
git pull
./scripts/run_public.sh
터미널 입력: Slack ID → 직원 ID → Bot Token → App Token
logs/cloudflare.log에서 https://xxxx.trycloudflare.com 확인
브라우저에서 주소 접속 → 로그인 → AI 비서 → 내 요청
Slack에서 봇에게 DM 전송 → 웹의 내 요청에서 결과 확인
Ctrl+C로 전체 종료
```

DB가 이미 초기화된 PC에서는 별도 명령이 필요 없다. 빈 DB에 시드를 다시 넣어야 할 때만 `db/reset.sh`를 수동 실행한다. 이 명령은 기존 데이터를 삭제하므로 주의한다.

## 3. Slack 봇 (`run_public.sh`·`SLACK=1`이면 함께 뜬다)

```bash
uv run python -m apps.slack_bot --check    # 토큰·scope·채널·매핑 점검
uv run python -m apps.slack_bot            # 봇 실행 (2번 서버가 떠 있어야 함)
uv run python -m apps.slack_bot --run-f1   # F1 자동 제안 한 바퀴만 돌리고 종료 (시연용)
pkill -f apps.slack_bot                    # 봇 끄기
```

- `.env`의 Slack 값을 바꾸면 봇도 재시작한다.

## 4. 외부 공개 (`scripts/tunnel.sh`, `run_public.sh`가 부름)

| 접속 주소 | 언제 |
| --- | --- |
| `https://xxxx.trycloudflare.com` (터미널·`logs/cloudflare.log`) | 항상. 켤 때마다 바뀐다 |
| 고정 https://nodi-admin.chltmddn5843.workers.dev | 이 PC가 Cloudflare 계정에 `wrangler login` 돼 있을 때. 마지막에 켠 PC 하나만 연결된다 |

- `APP_ENV=prod`에서만 열린다 (`run_public.sh`가 맞춰 준다).
- 어느 쪽이든 화면이 보여주는 데이터는 **터널을 켠 PC의 로컬 DB**다.
- `vite.config.js`의 `allowedHosts`가 `.trycloudflare.com` 전체를 허용한다. 서버만 재시작할 때는 터널을 끄지 않아도 된다.

## 자주 나는 문제

| 증상 | 원인 · 해결 |
| --- | --- |
| 로그인 시 `OperationalError ... port 5432` | DB가 꺼져 있거나 포트 매핑 누락 → 1번 명령 |
| Slack에 아무 반응 없음 | 봇 미실행 → 3번 명령 |
| Slack 답변이 "처리 중 문제가 생겼어요" | 에이전트 실패. `logs/agent.log` 확인. 흔한 원인은 `LLM_MODEL`의 공급사 키가 `.env`에 없거나, 셸(`~/.zshrc`)에 `export`된 예전 키가 `.env` 값을 덮어씀 (`load_dotenv`는 이미 있는 환경변수를 덮어쓰지 않는다) |
| Slack 요청 이력 확인 | PostgreSQL `agent.tasks` (아래 6절) |
| 터널 주소로 접속 시 "Blocked request" | `vite.config.js`의 `allowedHosts` 확인 |

## 6. 요청 이력 보기 (Slack·웹 공통)

`agent.tasks`에는 body(JSON 전체)에서 자동 계산되는 열이 있다: `status`, `channel`(slack·admin_ui·system), `requester_id`, `input`, `answer`, `tools`, `plan_id`, `approval`, `error`, `intent`, `feature_route`, `workflow`, `trace_id`.

```sql
SELECT created_at, channel, requester_id, status, input, answer, tools, feature_route, workflow
FROM agent.tasks ORDER BY created_at DESC;
```

- `feature_route`는 실제 호출된 도구가 속한 기능(F1~F4), `workflow`는 분류 → 호출 도구 → 승인 대기/완료 순서다. 작업이 끝나기 전에는 일부만 기록될 수 있다.
- 웹 화면: **AI 비서 → 내 요청**은 로그인한 직원 본인의 요청만(Slack에서 보낸 것 포함, 최근 10건). 다른 사람 요청은 승인 대기 건만 승인함에 나온다. 전체는 관리자 토큰으로 `GET /api/ai/tasks?mine=false`.
- 테스트(`uv run pytest`)는 별도 DB `capstone_test`를 쓰므로 이 이력을 지우지 않는다.
